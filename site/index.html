memtune · interactive demo

Choosing the L-BFGS memory parameter

L-BFGS keeps the last mem updates; JSOSolvers.jl uses mem = 5. Pick a test problem and a size, then watch the two-stage framework predict the solver's work and run time for every mem from 1 to 100 and recommend one. Measured runs are shown next to the predictions, and a one-step model (not in the paper) shows how to avoid the framework's bias towards very small mem.

How to read this, and its limits

  • Training data: 77 scalable unconstrained problems of OptimizationProblems.jl at variables, each solved for mem = 1 … 100 (21,802 runs). Problems marked test were never seen by the models; training problems were.
  • Why the framework often picks a very small mem: Stage 2 sees only the three Stage 1 numbers. Allocated memory grows with mem, and across problems it also grows with problem size, so Stage 2 learned that "more memory means slower". Within one problem its predicted run time therefore rises with mem, while the measured run time usually falls. The one-step model, which is not in the paper, predicts the run time directly from the 15 features and does not have this bias. Its settings were chosen by cross-validation on the training problems only.
  • Results on the 43 test problems (ratio to the best measured run; total = sum of the chosen runs' times):
  • Ratio to best: run time of a choice divided by the fastest measured run for that problem (1 = optimal in hindsight).
  • Limits: results come from one train/test split; the timing features depend on the machine that measured them; a single large fixed value (mem = 87, chosen with hindsight on the test problems) is a strong reference that no model here beats. See the paper.
  • Not covered: non-scalable (small, fixed-size) problems and sizes outside the training range; computing features for new problems live is on the roadmap.
