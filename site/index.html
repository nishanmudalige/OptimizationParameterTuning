Choosing the L-BFGS memory parameter

L-BFGS keeps the last mem updates; JSOSolvers.jl uses mem = 5. Pick a test problem and a size, then watch the two-stage framework predict the solver's work and run time for every mem from 1 to 100 and recommend one. Measured runs are shown next to the predictions.

1 The problem

The framework never runs the solver. It only sees these 14 features, measured once per problem (Julia: OptimizationProblems.jl, ADNLPModels.jl, expression trees).

2 Stage 1: predicted solver work

For every mem, a hybrid of a random forest (evaluation counts) and XGBoost (memory) predicts how much work L-BFGS will do. Lines are predictions, dots are measured runs.

3 Stage 2: predicted run time

The three Stage 1 predictions go into a second model that predicts the run time. The framework then picks the mem with the smallest predicted time.

How to read this, and its limits

  • Training data: 77 scalable unconstrained problems of OptimizationProblems.jl at variables, each solved for mem = 1 … 100 (21,802 runs). Problems marked test were never seen by the models; training problems were.
  • Ratio to best: run time of a choice divided by the fastest measured run for that problem (1 = optimal in hindsight).
  • Limits: results come from one train/test split; the timing features depend on the machine that measured them; the predicted run-time curve often does not follow the measured one, so a single large fixed value (mem = 87, chosen with hindsight) is a strong reference. See the paper.
  • Not covered: non-scalable (small, fixed-size) problems and sizes outside the training range; computing features for new problems live is on the roadmap.
